# Autopilot: continue

**Caveman, always.** Your first action, before any other tool call: invoke the `caveman` skill (`/caveman`), and keep it for the whole session. Every Agent-tool prompt you write starts with "Invoke the `caveman` skill first and answer terse." Persisted text stays plain prose.

This is the resume entry point of `/maxxfactory-run`. The run itself is unchanged: after the steps below you are the coordinator and follow `/maxxfactory-run`. **Load it now by invoking the `maxxfactory-run` skill with the Skill tool** (not by reading its file: a skill that was invoked is restored after a context compaction, a file that was read is not, and a coordinator that lost the rulebook stops showing the bars and stalls); skip its Setup section, which is done. Invoke it again after every compaction. In a harness without a Skill tool, read `../maxxfactory-run/SKILL.md` in full, and again after every compaction. `bin/<x>` means the `bin` directory next to this SKILL.md (the shared `bin/` of the maxxfactory repo); resolve it once and use absolute paths.

Setup is already done: never ask the owner the setup questions again (project, push, scope, exclusions, tiers). Everything you need is in `.maxxfactory/state.json`, `PLAN.md` and Linear. Ask only for something that is truly missing from all three, and record the answer as a decision.

## Steps

1. **Find the run.** The nearest `.maxxfactory/state.json` from the working directory (or `$AUTOPILOT_REPO`). None: say so and stop; the owner wants `/maxxfactory-run` (a first run) instead. Check out the project branch recorded there (`maxxfactory/<project-slug>`) if it is not the current one; never touch the default branch.
2. **Who you are.** `bin/run-model whoami --record`: this session's account becomes the protected one. If it differs from the previous `coordinator_account`, cooldowns recorded under the old account are stale: `bin/run-model reset` + `smoke` for it.
3. **Quotas and models.** `bin/run-model usage --apply`, `bin/run-model discover --apply`, `bin/harness check`, `bin/harness logins --min-hours <hours to the ETA + 24, at least 48>`, `bin/alert list`. Report CRITICAL alerts and what blocks a role; a login that is out or ends before the run does is fixed now, while the owner is here (the line gives the command), your own first.
3a. **Permissions.** `bin/permit check`; anything missing: show it, ask the owner's consent and apply now (`/maxxfactory-run` Setup step 0).
3b. **Human prerequisites.** Run the verify command of every `provided` row of the `Human prerequisites` table of `PLAN.md` (`/maxxfactory-run` Setup step 1b): a key that expired or an access that was revoked goes back to `missing`, and every missing row is asked in one message now, while the owner is here, with `! pbcopyenv <NAME>` for secrets. `deferred` rows: ask whether the owner can provide them now.
4. **Where it was.** `bin/pipeline status` (the bars and every in-flight ticket), `bin/decision check` (fix a `pending` entry first), `bin/decision list` (decisions since the last handoff), the latest project-level "handoff / resume point" comment in Linear, `git log --oneline -10` on the project branch, `git worktree list`.
5. **Restart the clock.** `bin/bgrun ls`. If `pipeline` is not running, first `bin/state migrate`: a project started before 2026-11-23 moves from `.autopilot/` to `.maxxfactory/` (`.autopilot` stays as a link); a no-op otherwise; refused while a background job runs (carry on: the project keeps working in `.autopilot/`, and the next resume moves it). Then start it as in `/maxxfactory-run` Setup step 8 (`bin/bgrun --name pipeline -- '<bin>/pipeline run'` in the tool's background mode), and `<bin>/pipeline wait-approval` as a second background job (your one wake-up job: approvals, attention, a change of the run verdict, a `TICK` every 10 minutes). Never start a second `pipeline run`.
6. **Recover interrupted tickets.** First `bin/gc`: it removes the worktrees of done tickets and the empty ones, and prints a `GC orphan` line for each worktree that holds work but is not in flight; decide each orphan now (merge, back in flight, or remove). For an in-flight ticket outside the clock whose model run died with the old session (no process for it in `ps`): `bin/rebase-wt <worktree>`, then a new round whose findings say "the previous round was interrupted, not rejected: keep the correct partial work in the tree and finish". Count it as a round. Approvals already in `.maxxfactory/pipeline/approved.txt` are merged now with `bin/pipeline merge`.
7. **Keep the machine up.** `bin/ci check` (exit 1: CI runs on pushes of the draft project branch; handle it as in `/maxxfactory-run` Setup step 7 before the next merge). `bin/spotlight check` (macOS: the folder that holds the repo and its `<repo>-wt`; exit 1: tell the owner and run `bin/spotlight fix`, as in `/maxxfactory-run` Setup step 9). A state.json written by an older version may carry a `worktrees_dir` elsewhere: it is ignored for new worktrees (`bin/pipeline wt` creates them in `<repo>-wt`), the tickets in flight finish where they are and `bin/gc` still collects them; `bin/spotlight check` lists that folder too while it exists. Then `caffeinate` (macOS) or `systemd-inhibit` (Linux) in the background, AC power check, `bin/docker-up` if the checks use containers.
8. **Tell the owner, in a few lines:** branch and compare/PR link, done since the last handoff, in flight, next in order, any `DECISION NEEDED:` lines, then `bin/pipeline status`, starting with its `RUN:` line in bold (RUNNING, DONE, STUCK, WAITING ON OWNER or STOPPED: see "The run verdict" in `/maxxfactory-run`). Post a short "resumed" note on the Linear handoff comment thread.
9. **Continue.** From here follow `/maxxfactory-run` from "The loop" onwards: same golden rules, same heartbeat, same end of session. The session ends only when every ticket in scope is done or explicitly blocked.
